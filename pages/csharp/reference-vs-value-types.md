## 概要

- C#の型は「参照型」と「値型」に大別され、変数が実際に保持するものが異なる
- ヒープとスタックという2つのメモリ領域の違いが、代入・引数渡しの挙動に直結する
- 読了後、なぜクラスとstructで代入の挙動が違うのかを説明できるようになる

## なぜ必要なのか

- メモリモデルを理解しないと、値が変わった／変わらなかった理由が分からずデバッグに時間がかかる
- 理解していれば、意図した挙動になる型（クラス/struct）を最初から選べる
- パフォーマンスチューニングの際、アロケーションを減らす判断基準にもなる

## 仕組みと動作原理

- **スタック**: メソッド呼び出しごとに確保・解放される領域。ローカル変数や値型の値が置かれる
- **ヒープ**: GC（ガベージコレクタ）が管理する領域。参照型のインスタンスはここに置かれる
- 参照型（クラス）の変数は「ヒープ上のインスタンスを指す参照」を保持する。代入すると参照がコピーされ、同じインスタンスを指す
- 値型（struct・int・boolなど）の変数は値そのものを保持する。代入すると値がコピーされ、別々の実体になる
- 値型でもクラスのフィールドとして持たれる場合はヒープ上（そのオブジェクトの一部）に置かれる。「値型=常にスタック」という理解は不正確

## 基本的な書き方とコード例

- 参照型の代入

```csharp
public class Counter { public int Value; }

var a = new Counter { Value = 1 };
var b = a; // 参照をコピー。aとbは同じインスタンスを指す
b.Value = 100;
Console.WriteLine(a.Value); // 100
```

- 値型の代入

```csharp
public struct Counter { public int Value; }

var a = new Counter { Value = 1 };
var b = a; // 値をコピー。aとbは別々の実体
b.Value = 100;
Console.WriteLine(a.Value); // 1
```

- 使い分けの判断基準
  - 複数箇所で同じインスタンスを共有・変更したい → 参照型（クラス）
  - コピーされても困らない、むしろコピーの独立性がほしい → 値型（struct）

## よくある誤用・バグ

- **「値型は常にスタックに乗る」という誤解**
  - structでも、クラスのフィールドや配列の要素になっている場合はヒープ上に確保される

```csharp
// NG: 常にスタックに乗ると思い込み、大量生成しても軽いと誤解する
public class Container
{
    public Point[] Points = new Point[1_000_000]; // structの配列だがヒープ上に確保される
}
```

```csharp
// OK: 「型」ではなく「置かれる場所（ローカル変数か、配列・フィールドの一部か）」で決まると理解する
// 大量データの場合はメモリレイアウトの実測やSpan<T>の活用を検討する
```

- **参照型の変更が呼び出し元にも影響することを見落とす**
  - メソッド引数として渡したクラスインスタンスを変更すると、呼び出し元の値も変わる

```csharp
// NG: 呼び出し元への影響を意図せず発生させる
void Reset(Counter c) => c.Value = 0; // クラスの場合、呼び出し元のインスタンスも0になる
```

```csharp
// OK: 影響を防ぎたいなら新しいインスタンスを返す設計にする
Counter Reset(Counter c) => new Counter { Value = 0 };
```

## パフォーマンス・セキュリティ上の注意点

- ヒープへの確保が増えるとGCの実行頻度が上がり、アプリ全体のスループットに影響する
- 大量の小さいオブジェクトをクラスで生成し続けると、GC負荷が目立ちやすい
- ループ内で大量に生成する値はstruct化やSpan\<T\>の活用でヒープ確保を抑えられる場合がある
