## この記事でわかること

- イミュータブル設計とミュータブル設計の違いを説明できる
- record の with式を使って、元のインスタンスを変えずに新しい値を作るコードを書ける
- プロパティは変更不可なのに中のコレクションだけ書き換えられてしまう、という落とし穴を避けられる
- `ImmutableList<T>` を使って、パフォーマンスも意識した不変なコレクションを扱える

## 一言でいうと

イミュータブル（不変）とは、一度作ったら中身が二度と変わらないもの、という設計方針です。

レジで受け取ったレシートを思い浮かべてください。あとで商品の値段が変わったとしても、もう印刷されたレシートの数字が書き換わることはありません。プログラムの世界でも同じで、イミュータブルなオブジェクトとは、生成した後はプロパティやフィールドの値を書き換えられないオブジェクトのことです。値を変えたいときは、既存のインスタンスをそのまま書き換えるのではなく、新しいインスタンスを作って返します。ただし、レシートの紙と違って、オブジェクトの不変性は自動で保証されるわけではなく、自分でそう設計して初めて成り立つ点が異なります。

## どんなときに困るのか

注文を表すクラスに、商品名を並べる`List<string>`を持たせて、複数の画面に同じインスタンスを渡して使い回していたとします。ある画面で商品を1つ削除したところ、別の画面で表示していたはずの注文の中身まで、いつの間にか変わってしまいました。原因を追うと、渡していたのはコピーではなく同じ`List<string>`そのもので、どちらか一方が変更すればもう一方にも影響していたのです。バグの原因を1行ずつ追うだけで半日かかった、という経験がある人も多いはずです。

生成した後は絶対に値が変わらないと分かっているオブジェクトなら、どこで誰が使っていても安心して共有できます。変更を許さないというルールそのものが、追跡すべき可能性を減らしてくれるのです。

## 動かしてみる

```csharp
var p1 = new Point(0, 0);
var p2 = p1 with { X = 3 };

Console.WriteLine(p1);
Console.WriteLine(p2);

public record Point(int X, int Y);
```

```
Point { X = 0, Y = 0 }
Point { X = 3, Y = 0 }
```

`p1 with { X = 3 }`は、`p1`を書き換えているわけではありません。`p1`の値をコピーしたうえで`X`だけ`3`に変えた、まったく新しいインスタンスを作って`p2`に代入しています。だから`Console.WriteLine(p1)`を呼んでも、`p1`は最初に作ったときのまま`X = 0`です。変更したい場合は「変更後の新しいインスタンスを受け取る」のであって、「今あるインスタンスが変わる」のではありません。

## 仕組み

record（『レコード(record)の基本』で説明した、値の等価性やwith式を自動生成する機能を持つ型）の位置引数構文で定義したプロパティは、既定で`init`になります。`init`は「コンストラクタの中でだけ値を設定でき、それ以降は変更できない」というアクセサなので、一度生成したインスタンスのプロパティはもう書き換えられません。`with`式は、この`init`プロパティに新しい値を設定し直した、別のインスタンスを作る構文です。readonly struct（『readonly structの基本』で説明した、すべてのフィールドが生成後に変更不可であることをコンパイラが保証する構造体）も、同じ考え方を値型側で実現する機能です。

不変オブジェクトの中身がすべて`int`や`string`のような単純な値なら、これだけで安全です。ただし中に`List<T>`のような、あとから中身を書き換えられるコレクションを持たせると話が変わってきます。プロパティ自体は`init`で変更できなくても、そのプロパティが指している`List<T>`の中身は、外から`Add`や`Remove`を呼ばれると変わってしまいます。「よくある間違い」で詳しく見ていきます。

- コンストラクタと`init`プロパティ（またはreadonlyフィールド）だけでオブジェクトを組み立てる
- 値を変えたい操作は、既存のインスタンスを書き換えず、新しいインスタンスを返す形にする
- コレクションを持たせる場合は、コレクション自体も書き換えられない型にする

## 実務での使い方

金額や座標のような「値そのもの」を表すオブジェクトは、不変にしておくと安全です。

```csharp
var price = new Money(1000m);
var discounted = price.Add(-100m);

Console.WriteLine(price.Amount);
Console.WriteLine(discounted.Amount);

public record Money(decimal Amount)
{
    public Money Add(decimal amount) => this with { Amount = Amount + amount };
}
```

```
1000
900
```

`price`は値引き処理を呼んだ後も`1000`のままなので、元の金額を持っていた別のコードには影響しません。プログラムの中では、複数のスレッド（同時に動く処理の流れ）が同時に動くことがありますが、不変なオブジェクトなら値が変わらないので、ロックのような仕組みを使わなくても複数のスレッドから安全に読み取れます。これをスレッドセーフ（複数の処理が同時に読み書きしてもデータが壊れない性質）と呼びます。

- 金額・座標・日付範囲のような値オブジェクトは、不変にしておく
- 頻繁に少しずつ更新される大きな状態は、単純な不変設計だけでなく後述の`ImmutableList<T>`のような専用の型も検討する

## よくある間違い

### プロパティは不変でも、中のコレクションは可変のまま持ってしまう

`record`で定義したプロパティは書き換えられないと思っていても、プロパティの型が`List<string>`のような可変なコレクションだと、そのコレクションの中身は外から自由に変更できてしまいます。

```csharp
// NG: プロパティはinitだが、Listの中身は外から変更できる
var cart = new Cart(new List<string> { "apple" });
cart.Items.Add("banana");

Console.WriteLine(cart.Items.Count);

public record Cart(List<string> Items);
```

```
2
```

`Cart`自体は不変のつもりで作っても、`cart.Items.Add("banana")`はコンパイルエラーにならず2件に増えてしまいます。直すには、コレクションの型自体を「追加・削除するメソッドを持たない型」に変えます。

```csharp
// OK: 変更用のメソッドを持たない型にする
var cart = new Cart(new List<string> { "apple" });
// cart.Items.Add("banana"); // コンパイルエラーになる: CS1061

Console.WriteLine(cart.Items.Count);

public record Cart(IReadOnlyList<string> Items);
```

```
1
```

`IReadOnlyList<string>`には`Add`や`Remove`が無いため、`cart.Items.Add(...)`はコンパイルエラーになります。プロパティの型を変えるだけで、うっかり追加してしまう事故を防げます。

### IReadOnlyListにしても、渡した元のListを書き換えられると中身が変わってしまう

先ほどの直し方には、まだ落とし穴があります。コンストラクタに渡した`List<string>`そのものを、呼び出し元がまだ持っている場合です。

```csharp
// NG: 渡した元のListを後から書き換えると、Basket側にも反映されてしまう
var items = new List<string> { "apple" };
var basket = new Basket(items);
items.Add("banana");

Console.WriteLine(basket.Items.Count);

public record Basket(IReadOnlyList<string> Items);
```

```
2
```

`basket.Items`の型は`IReadOnlyList<string>`ですが、実体は呼び出し元が持つ`items`と同じ`List<string>`です。`basket`側からは変更できなくても、`items`側から`Add`すれば同じ実体が変わります。これを防ぐには、最初から書き換える手段そのものがないコレクション型を使います。

```csharp
// OK: ImmutableList<T>なら、そもそも中身を書き換える手段が無い
using System.Collections.Immutable;

var items = ImmutableList.Create("apple");
var basket = new Basket(items);
var updated = items.Add("banana");

Console.WriteLine(basket.Items.Count);
Console.WriteLine(updated.Count);

public record Basket(ImmutableList<string> Items);
```

```
1
2
```

`ImmutableList<T>`の`Add`は、`items`自体を書き換えるのではなく、要素を1つ追加した別のインスタンスを新しく返します。だから`items.Add("banana")`を呼んでも`items`自体は変わらず、`basket.Items.Count`は`1`のままです。追加された結果がほしいときは、戻り値の`updated`を使います。

## 注意点

不変なオブジェクトを変更するたびに、内部では新しいインスタンスが1つ作られます。頻繁に更新する場面でこれを繰り返すと、メモリの使用量が増える場合があるので、まずは動かしてみて、問題になってから見直すくらいの態度で十分です。

`ImmutableList<T>`は、要素を追加するときに丸ごとコピーするのではなく、変更のない部分は元のインスタンスと共有し、変更された部分だけ新しく作る仕組み（構造共有）を使っています。とはいえ単純な`List<T>`に比べると、追加や参照に少し余分な処理がかかるので、大量の要素を高頻度に更新する場面では実際に計測してから採用を判断してください。

## 用語まとめ

| 用語 | 意味 |
|---|---|
| イミュータブル（不変） | 一度生成したら、プロパティやフィールドの値を二度と変更できないという設計方針 |
| ミュータブル（可変） | 生成した後もプロパティやフィールドの値を自由に書き換えられる設計方針 |
| `IReadOnlyList<T>` | 追加・削除用のメソッドを持たない読み取り専用のリスト。ただし元の`List<T>`が別の場所で書き換えられると中身は変わる |
| `ImmutableList<T>` | 要素を追加・削除すると、元のインスタンスは変えずに新しいインスタンスを返すリスト |
| 構造共有 | 新しいインスタンスを作るとき、変更のない部分は元のインスタンスと共有し、変更された部分だけ新しく作る仕組み |
| スレッド | プログラムの中で同時に動く処理の流れのこと |
| スレッドセーフ | 複数のスレッドが同時に同じオブジェクトを読み書きしても、データが壊れたり想定外の値にならない性質 |
