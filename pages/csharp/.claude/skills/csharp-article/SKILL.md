# C#入門記事ジェネレータ

C#を書き始めて数週間〜数か月の人が、5分で読んで翌日から現場で使える記事を書く。読み物ではなく、手元に置いて見返すメモ。

読者は変数・if・for・メソッド・引数・戻り値・文字列・配列・`List<T>` は使える。それ以外は知らないものとして扱い、見下さない。

## 入力

`$ARGUMENTS` にテーマと、あれば追加指示。テーマが無ければ1回だけ確認する。それ以外はすべて自分で判断する。

## 手順

1. **既存記事を調べる**: 記事ディレクトリ（このskillがある `.claude/` の親、通常 `pages/csharp/`）直下の `*.md` の frontmatter を読む。同テーマの記事があれば作らず報告して終了（上書き指示があれば上書き）。同カテゴリか近い `order` の記事を1〜2本読み、形式と文体の基準にする。
2. **前提トピックを分ける**: 本文を読むのに必要な知識を挙げ、次のいずれかにする。
   - 読者が既に知っている基礎 → 説明しない
   - 既存記事がある → `prerequisites` に書き、本文で再説明しない
   - 記事が無く、1〜2文の定義では足りない → **前提記事として合わせて生成する**。1〜2文で済むなら本文中で定義する

   前提記事は本記事より小さい `order`。前提の前提も生成してよいが深さは2段階まで。1回の実行で本記事を含め最大6本、超えた分は本文で1文定義し「未作成の前提記事」として報告する。既存記事の frontmatter は変更しない。
3. **メタデータを決める**（後述）。
4. **書く**: 「記事の形式」「文体」「コード例」に従う。本文は日本語。
5. **コードを検証する**: `dotnet` が使えれば、スクラッチディレクトリにコンソールプロジェクトを作り、各コード例を貼って `dotnet build` を通す。「エラーになる」と説明したNG例は、実際にそのエラーが出ることを確認する。通らなければ記事を直す。`dotnet` が無ければ完了報告に書く。
6. **出力する**: 記事ディレクトリ直下に前提記事から順に保存する。他の場所には出力しない。完了報告は、記事ごとのパスと frontmatter の内容、前提記事を生成した理由と未作成の前提記事、コード検証の有無と結果だけ。

## メタデータ

frontmatter のキーは次の6つだけ。

- **title**: 日本語20文字前後。内容が一目で分かる形（「○○の基本」「○○と○○の違い」）
- **category**: `文法` / `設計` / `パフォーマンス` / `非同期` / `LINQ` / `テスト` / `環境・CLI` のいずれか
- **order**: 難易度1〜100。「その記事を読める人が既に何ができるか」で決め、前提記事は必ず本記事より小さくする
  - 1〜20: 変数・if・forが書ける。型・クラス・メソッド・プロパティ・参照と値・null の基本
  - 21〜40: クラスを定義できる。コレクション・例外・インターフェース・ジェネリクス・LINQ基礎・null安全・等価性
  - 41〜60: 業務コードを読める。async/await・DI・record・パターンマッチ・単体テスト・不変設計
  - 61〜80: 業務コードを書ける。並行処理・Span/Memory・計測・リフレクション・式木
  - 81〜100: 設計判断ができる。unsafe・GC内部・ソースジェネレータ・ロックフリー
- **prerequisites** / **next**: 各項目は `file`（拡張子付きファイル名）と `note`（前提なら何が分かっていれば十分か、次なら読む理由を一言）。各0〜3件
- **related**: 前提でも次でもない関連記事のファイル名。0〜3件、無ければ `[]`
- 上記3キーに書けるのは、実在するか同じ実行で生成するファイル名だけ。記事間のリンクは frontmatter にのみ書き、本文には書かない
- **ファイル名**: ケバブケース英名2〜5単語 + `.md`

## 記事の形式

次の要素をこの順で含める。見出しの文言は固定しない。本文はコードを除いて800〜1,500文字（読了5分）。超えるなら削るか記事を分ける。

1. **定義**: 何であるかを短い文で述べ、主な性質・目的を箇条書き2〜3個
2. **なぜ必要か**（自明でないときだけ）: 3文以内。これが無いと何が困るかを1つ
3. **コード**: 動く最小のコードと出力。説明はコード中のコメントを優先し、地の文はコードに現れない前提や代替パターンの補足に限る
4. **最低限の理解**: 「これだけ守れば事故らない」運用ルールを箇条書き3〜5個、1項目1〜2文
5. **落とし穴**（テーマ固有のものがあるときだけ）: 現場で起きる間違い1〜2個。NG→OKの順で、NGには出力かエラーを示す
6. **課題**: 手を動かす小さな課題を1つ。解答は書かない

記事の目的に寄与しないセクション（用語集・理解度チェック・まとめ・一般論の注意点）は作らない。前提記事の内容は再説明せず、その用語を知らないと直後の文が読めない箇所に限り、記事名を添えて1行で再掲する。純粋なmarkdownで書く。

## 文体

- **シンプルさと本質を両立させる。**「〜のミスを防げる」「〜が楽になる」という効果だけで理由づけを終わらせず、その機能が扱う概念が何のために存在するかを平易な言葉で書く。本質を書くために専門用語や長い前置きが必要になるなら、一段簡略化して平易な言葉を選ぶ
  - 例: `class` の「なぜ必要か」は「引数の順序ミスを防ぐため」ではなく「複数のデータと振る舞いからなる概念に名前を与え、ひとまとまりのオブジェクトとして扱うため」
- 常体と体言止め。1文40文字前後、1段落2〜4文。因果は段落、並列は箇条書き
- **太字**は「これだけ覚えればいい」1〜2箇所だけ
- たとえ話は書かない。ラベルとして名詞1語を使うなら、直後に本物の用語で言い直す
- 目的を先に、仕組みは後に。仕組みは使うために必要な範囲で止める
- 正確さより伝わることを優先し、省いた例外は「厳密には〜だが」と1文で断る
- 網羅性より現場で遭遇する頻度。中身のない前置きと締めは書かない
- 専門用語は初出時に定義する。定義できないなら使わない
- 一般的な概念は日本語で書き、C#のキーワード・型名そのものはバッククォートで囲む。日本語表記が定着していない用語（`struct`、`record` など）は概念を指すときも英語のまま。同じ記事内で表記を揺らさない
