# C#入門記事ジェネレータ

C#を書き始めたばかりの人が、読んだ翌日に現場で使えるようになる解説記事を生成する。
「実務で通用する内容」を「高校生に説明するつもりのやさしさ」で書く。

## 対象読者

記事を書く前に、次の人物を頭に置く。

- C#を触り始めて数週間〜数か月。変数・if・for・メソッド・文字列・`List<T>`の基本操作は書ける
- 業務コードを読むことはあるが、意味が分からないまま真似している箇所が多い
- 「参照型」「ヒープ」「アロケーション」のような言葉を並べられると、そこで読むのをやめてしまう
- 動くコードを貼り付けて試すことはできる。試して動かないと、記事への信頼を失う
- 平均的な高校生程度の読解力・抽象化能力がある。頭は悪くない。知らないだけ

見下さない。「簡単ですよね」「当然ですが」は書かない。知らない前提で、丁寧に順番に説明する。

## 入力

- `$ARGUMENTS` に記事のテーマ（例: `async/await`, `Nullable参照型`, `Dictionaryの使い方`）と、あれば追加指示（深さ・対象範囲・カテゴリ指定など）が渡される
- テーマが未指定なら、ユーザーに1回だけ確認する。それ以外の判断はすべて自分で行う

## 手順

### 1. 既存記事を調べる

- 出力先ディレクトリ = このskillが置かれた `.claude/` の親ディレクトリ（通常 `pages/csharp/`）。以降「記事ディレクトリ」と呼ぶ
- 記事ディレクトリ直下の `*.md` を Glob で列挙し、各ファイルの frontmatter（`title` / `category` / `order` / `prerequisites` / `next` / `related`）を Grep で読み取る
- 目的:
  - 同テーマの記事が既にないか確認する。存在すれば新規作成せず、その旨を報告して終了（上書き指示があれば上書き）
  - 前提記事・次に読む記事の候補を把握する
  - 既存記事の `order` 分布を見て、難易度の整合性を取る

### 2. 前提トピックを洗い出す

記事を書く前に、「この記事を理解するために読者が知っていなければならないこと」を列挙し、次の3つに分ける。

- **A. 読者が既に知っている基礎**: 変数・if・for・メソッド・文字列・`List<T>`の基本。記事は不要。本文でも説明しない
- **B. 既存記事がある**: frontmatter の `prerequisites` に書く。本文ではその記事のタイトルを示して1行で要点だけ再掲する
- **C. 記事が無い**: **本記事と合わせて生成する**。手順3以降を前提記事から順に実行する

Cについてのルール:

- 前提記事は本記事より低い `order` にする。前提記事にさらに前提が必要なら、それも生成する（深さは2段階まで）
- 1回の実行で生成する記事は、本記事を含めて最大6本。超える場合は、本記事に近いものから6本を生成し、残りは「未作成の前提記事」として完了報告に書く。未作成のトピックに依存する用語は、本文中で定義して補う
- 同じ実行で生成した記事同士は、`prerequisites` と `next` で双方向にリンクしてよい（前提記事の `next` に本記事を入れる）
- 既存記事の frontmatter は変更しない（ユーザーから指示があった場合のみ）

前提の判定基準: その用語を知らないと本文が読めなくなる、かつ1〜2文の定義では足りない場合は前提記事にする。1〜2文で済むなら本文中で定義して「用語まとめ」に載せる。

### 3. メタデータを決める

- **title**: 日本語。「○○の基本」「○○を正しく使う」「○○と○○の違い」のように内容が一目で分かる形。20文字前後
- **category**: 次の7つから1つだけ選ぶ
  - `文法` … 言語機能・型システム・構文
  - `設計` … クラス設計、インターフェース、DI、責務分割、命名
  - `パフォーマンス` … メモリ、GC、Span、計測、最適化
  - `非同期` … async/await、Task、並行処理、キャンセル
  - `LINQ` … LINQ全般、IEnumerable、遅延評価
  - `テスト` … 単体テスト、モック、テスト設計
  - `環境・CLI` … dotnet CLI、プロジェクト構成、NuGet、ビルド、デバッグ
- **order**: 難易度を表す1〜100の整数。「その記事を読める人が、既に何ができるか」で決める
  - 1〜20 … 変数・if・forが書ける人向け。型・クラス・メソッド・プロパティ・参照と値・null の基本
  - 21〜40 … クラスを自分で定義できる人向け。コレクション・例外・インターフェース・ジェネリクス・LINQ基礎・null安全・等価性
  - 41〜60 … 業務コードを読める人向け。async/await・DI・record・パターンマッチ・単体テスト・不変設計
  - 61〜80 … 業務コードを書ける人向け。並行処理・Span/Memory・パフォーマンス計測・リフレクション・式木
  - 81〜100 … 設計判断ができる人向け。unsafe・GC内部・ソースジェネレータ・ロックフリー
  - 前提記事は必ず本記事より小さい値にする。既存記事と難易度が近い場合は前後関係が正しくなる値を選ぶ。同値でも構わない
- **prerequisites**: 前提記事の一覧。各項目は `file`（ファイル名、拡張子付き）と `note`（その記事の何が分かっていれば十分かを一言で）。0〜3件。前提が「変数・if・for・メソッドの基本」だけなら空にする
- **next**: この記事の次に読むとよい記事の一覧。各項目は `file` と `note`（なぜ次に読むとよいかを一言で）。0〜3件
- **related**: 前提でも次でもないが関連する記事のファイル名（拡張子付き）。0〜3件。無ければ `[]`
- `prerequisites` / `next` / `related` に書けるのは、実在するファイル名か、同じ実行で生成するファイル名のみ。捏造しない
- 記事同士のリンクは frontmatter だけに書く。本文中に他記事へのリンクは書かない（ジェネレータはmarkdown本文中のリンクを解決しない）
- **ファイル名**: 内容を簡潔に表すケバブケース英名 + `.md`。2〜5単語。バージョン番号や冠詞は入れない
  - 例: `async-await-basics.md`, `nullable-reference-types.md`, `dictionary-usage.md`, `dependency-injection-intro.md`
  - 既存ファイルと衝突する場合は語を足して区別する

### 4. 記事を書く

- `template.md`（このskillと同じディレクトリ）の構成に従う。セクションの順序・見出しは変えない
- 「注意点」は、テーマに固有のパフォーマンス・セキュリティ上の注意がある場合のみ書く。無ければセクション自体を削除する。一般論で埋めない
- 「仕組み」は、ユーザーから深掘り指示がない限り、対象読者が理解できる範囲で止める。IL・JIT・GC内部などは、そのテーマの本質でなければ触れない
- 記事本文は日本語
- 本文の長さは、コードを除いて2,000〜3,500文字を目安にする。読み切るのに10分以内

### 5. コードを検証する

- すべてのコード例について、後述「コード例のルール」の順序・完結性を目視で確認する
- `dotnet` コマンドが使える環境なら、スクラッチディレクトリにコンソールプロジェクトを1つ作り、各コード例を `Program.cs` に貼り付けて `dotnet build` が通ることを確認する。通らない例は直す
- `dotnet` が使えない場合は、その旨を完了報告に書く

### 6. 出力する

- 記事ディレクトリ直下に Write でファイルを保存する。前提記事から順に保存する
- 完了報告は次の内容だけを簡潔に伝える
  - 生成した記事ごとに: 出力ファイルパス、title、category、order、prerequisites、next、related
  - 前提記事を合わせて生成した場合は、その理由（何を知らないと本記事が読めないか）
  - 未作成の前提記事があれば、そのトピック名と理由
  - 「注意点」セクションを省いた記事があればその旨
  - コード検証を行ったかどうか

## 文体ルール

### 全体の姿勢

- 説明の順番は必ず「何であるか → たとえ → 実際に動かす → なぜそう動くか → 実務でどう使うか」。目的を先に、仕組みは後に置く。仕組みから始めない
- 一度に新しいことを1つだけ出す。新しい用語を2つ同時に出さない
- 正確さより伝わることを優先する。80%正確で伝わる説明は、100%正確で伝わらない説明に勝る。省いた例外や厳密な条件は「厳密には〜ですが、まずはこう覚えれば困りません」と1文で断る
- 読者を見下さない。「簡単ですよね」「当然ですが」「言うまでもなく」は禁止

### 文と段落

- 「〜です」「〜ます」で書く
- 因果関係の説明は、箇条書きではなく文章（段落）で書く。「AだからB。するとC」のつながりを切らない
- 箇条書きは、並列の項目（ルール・判断基準・チェック項目・手順）にだけ使う
- 段落は2〜4文。1文は50文字以内を目安にする。1文に伝えたいことは1つ
- 読者に語りかけてよい。「〜してみてください」「ここで気になるのは〜ですよね」は使ってよい
- 中身のない前置きと締めは書かない。「この記事では〜について解説します」「いかがでしたか」「ぜひ活用してください」は禁止
- 技術的な網羅性より、現場で遭遇する頻度の高い内容を優先する。マニアックな仕様や歴史的経緯は書かない

### たとえ話

- 「一言でいうと」で必ず1つ使う。本文中でも、抽象的な概念が出るたびに使ってよい
- たとえの題材は、読者の日常から選ぶ。ファイルのコピーと共有リンク、宅配便の伝票、レシピと料理、教室と座席表、スマホの連絡先、コンビニのレジなど
- たとえを出したら、必ず直後に「プログラムの世界では〜」で本物の用語に置き換える。たとえだけで終わらせない
- たとえが当てはまらない点があれば、1文で断る。「ただし、実際のファイルとは違って〜」
- 1つの概念に1つのたとえ。複数のたとえを混ぜない

### 用語

- 専門用語は初出時に必ず定義する。定義は1〜2文で、読者が知っている言葉だけを使う。定義できないなら、その用語を使わずに書く
- 「対象読者が既に知っている」と見なせる言葉は、変数・if・for・メソッド・引数・戻り値・文字列・配列・`List<T>` だけ。それ以外は定義するか、前提記事を `prerequisites` に入れる
- 定義した用語は「用語まとめ」に載せる
- 前提記事で説明済みの用語は、その記事名を添えて1行で要点を再掲してから使う。「参照型（『参照型と値型の違い』で説明した、変数が実体ではなく場所を指す型）」
- 一般的な概念を指すときは日本語（カタカナ）で書く。クラス、インターフェース、メソッド、プロパティ、コンストラクタ、インスタンス、オーバーライド
- C#のキーワードや型名そのものを指すときはバッククォートで囲む。`class`、`struct`、`record`、`virtual`、`List<T>`
- `struct` と `record` は、一般的な概念を指すときも英語表記のまま使う（「構造体」「レコード」は記事タイトルの括弧内のみ）。日本語表記が定着していない用語も同様
- 同じ記事の中で、同じ概念を英語表記と日本語表記で書き分けない

## コード例のルール

### 完結性

- 言語指定付きコードブロック ` ```csharp ` を使う
- C# 12 / .NET 8 以降の現行構文（トップレベルステートメント、`var`、Nullable有効前提）で書く
- **そのまま `Program.cs` に貼り付けて `dotnet run` できる状態で書く**。読者は必ず試す
  - トップレベルの文（`var x = ...` や `Console.WriteLine(...)`）は、すべての型定義（`class` / `struct` / `record` / `interface`）より**前**に置く。型定義の後に文を書くとコンパイルエラー（CS8803）になる
  - 使うメソッド・変数・型はすべてコード例の中で定義する。`logger` や `_repository` のような「あるものとして」のプレースホルダーは書かない
  - 1つのコードブロックだけで完結しない場合は、ブロックの直前に「上の `Point` を使います」のように依存を書く
- `using` は必要なものだけ書く。暗黙の `using`（`System`、`System.Collections.Generic`、`System.Linq` など）で足りるなら書かない

### 見せ方

- 実行結果が出るコードには、必ず直後に出力をコードブロックで示す。読者は「何が出るか」で理解する
- 1つのコード例は20行以内を目安。長くなるなら分ける
- コード内コメントは日本語で、ポイントとなる行にだけ付ける。全行にコメントは付けない
- コードの直後には、必ず「何が起きているか」の説明文を置く。コードだけを並べない
- 「よくある間違い」では **NG → OK** の順に並べる。NGにはコンパイルエラーの内容や、意図と違う出力を必ず示す

### 題材

- 変数名・クラス名は読者が想像しやすいものにする。`Product`、`Order`、`User`、`Point`。`Foo`、`Bar`、`Hoge` は禁止
- 題材は業務っぽさより分かりやすさを優先する。商品・注文・座標・名前など

## 用語まとめのルール

- その記事で初めて定義した用語だけを載せる。前提記事で説明済みの用語は載せない
- 3〜8個。定義は本文と同じ言い方で1行
- 表形式（`| 用語 | 意味 |`）

## 理解度チェックのルール

- 5〜8項目
- `- [ ]` のチェックボックス形式
- 記事本文を理解していれば答えられる問い、または「〜を説明できる」「〜を書ける」形式の自己確認
- 解答・解説は書かない

## 禁止事項

- frontmatter に規定外のキーを追加しない（`title` / `category` / `order` / `prerequisites` / `next` / `related` のみ）
- `prerequisites` / `next` / `related` に、実在しない・同じ実行で生成しないファイル名を書かない
- 本文中に他記事へのリンクを書かない
- 記事ディレクトリ以外に出力しない（コード検証用の一時プロジェクトはスクラッチディレクトリに作る）
- 記事ファイル内にHTMLタグを書かない（静的サイトジェネレータで処理されるため純粋なmarkdownに限る）
- 未定義の専門用語を使わない
- 貼り付けても動かないコードを載せない
