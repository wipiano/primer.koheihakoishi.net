# C#入門記事ジェネレータ

ジュニアエンジニアが「明日から実務で使える」ことを最優先にした、完全箇条書きスタイルのC#解説記事を生成する。

## 入力

- `$ARGUMENTS` に記事のテーマ（例: `async/await`, `Nullable参照型`, `Dictionaryの使い方`）と、あれば追加指示（深さ・対象範囲・カテゴリ指定など）が渡される
- テーマが未指定なら、ユーザーに1回だけ確認する。それ以外の判断はすべて自分で行う

## 手順

### 1. 既存記事を調べる

- 出力先ディレクトリ = このskillが置かれた `.claude/` の親ディレクトリ（通常 `pages/csharp/`）。以降「記事ディレクトリ」と呼ぶ
- 記事ディレクトリ直下の `*.md` を Glob で列挙し、各ファイルの frontmatter（`title` / `category` / `order`）を Grep で読み取る
- 目的:
  - 同テーマの記事が既にないか確認する。存在すれば新規作成せず、その旨を報告して終了（上書き指示があれば上書き）
  - 関連記事（前提知識・同カテゴリ・次のステップ）を最大5件選ぶ
  - 既存記事の `order` 分布を見て、難易度の整合性を取る
- 既存記事が0件なら `related: []` とする

### 2. メタデータを決める

- **title**: 日本語。「○○の基本」「○○を正しく使う」のように内容が一目で分かる形。20文字前後
- **category**: 次の7つから1つだけ選ぶ
  - `文法` … 言語機能・型システム・構文
  - `設計` … クラス設計、インターフェース、DI、責務分割、命名
  - `パフォーマンス` … メモリ、GC、Span、計測、最適化
  - `非同期` … async/await、Task、並行処理、キャンセル
  - `LINQ` … LINQ全般、IEnumerable、遅延評価
  - `テスト` … 単体テスト、モック、テスト設計
  - `環境・CLI` … dotnet CLI、プロジェクト構成、NuGet、ビルド、デバッグ
- **order**: 難易度を表す1〜100の整数。目安:
  - 1〜20 … 変数・型・制御構文・メソッド・クラスの基本。プログラミング初学者レベル
  - 21〜40 … コレクション・例外・インターフェース・ジェネリクス・LINQ基礎・null安全。業務コードを読める
  - 41〜60 … async/await・DI・record・パターンマッチ・単体テスト。業務コードを書ける
  - 61〜80 … 並行処理・Span/Memory・パフォーマンス計測・リフレクション・式木。設計判断ができる
  - 81〜100 … unsafe・GC内部・ソースジェネレータ・ロックフリー。ライブラリ作者レベル
  - 既存記事と難易度が近い場合は前後関係が正しくなる値を選ぶ。同値でも構わない
- **related**: 手順1で選んだ既存記事のファイル名（拡張子付き）。実在するファイル名のみ書く。捏造しない
- **ファイル名**: 内容を簡潔に表すケバブケース英名 + `.md`。2〜5単語。バージョン番号や冠詞は入れない
  - 例: `async-await-basics.md`, `nullable-reference-types.md`, `dictionary-usage.md`, `dependency-injection-intro.md`
  - 既存ファイルと衝突する場合は語を足して区別する

### 3. 記事を書く

- `template.md`（このskillと同じディレクトリ）の構成に厳密に従う。セクションの順序・見出しは変えない
- 「パフォーマンス・セキュリティ上の注意点」は、テーマに固有の注意点がある場合のみ書く。無ければセクション自体を削除する。一般論で埋めない
- 「仕組みと動作原理」は、ユーザーから深掘り指示がない限り、ジュニアエンジニアが理解できる範囲で止める。IL・JIT・GC内部などは、そのテーマの本質でなければ触れない
- 記事本文は日本語

### 4. 出力する

- 記事ディレクトリ直下に Write でファイルを保存する
- 既存記事の frontmatter は変更しない（双方向リンクの追加は、ユーザーから指示があった場合のみ）
- 完了報告は次の内容だけを簡潔に伝える: 出力ファイルパス、title、category、order、related に入れた記事、注意点セクションを省いた場合はその旨

## 文体ルール

- **完全箇条書き**。見出しとコードブロック以外はすべて `-` の箇条書き。段落形式の文章は書かない
- 1項目1事実。1項目は原則1〜2文、60文字以内を目安
- ネストは最大2階層まで
- 冗長な導入・締め・ストーリー・比喩・雑談は書かない。「この記事では〜」「〜してみましょう」「いかがでしたか」は禁止
- 文末は簡潔に。体言止め、または「〜する」「〜になる」「〜が必要」。「〜です・ます」は使わない
- 実務で判断が必要な箇所は「〜の場合は〜を選ぶ」と判断基準を明示する
- 技術的な網羅性より、現場で遭遇する頻度の高い内容を優先する。マニアックな仕様や歴史的経緯は書かない
- 用語は初出時に1行で定義する。英語の専門用語はそのまま使い、無理に和訳しない

## コード例のルール

- 言語指定付きコードブロック ` ```csharp ` を使う
- C# 12 / .NET 8 以降の現行構文（トップレベルステートメント、file-scoped namespace、`var`、Nullable有効前提）で書く
- そのまま貼り付けてビルド・実行できる最小単位。不要なクラス・usingは付けない
- 1つのコード例は20行以内を目安。長くなるなら複数に分ける
- コード内コメントは日本語で、ポイントとなる行にだけ付ける
- 「よくある誤用・バグ」では **NG例 → OK例** の順に並べ、何が問題かをコメントまたは直後の箇条書きで1行で示す
- 出力例が重要な場合はコードブロックの直後に `// 出力:` 形式で示す

## 理解度チェックリストのルール

- 5〜8項目
- `- [ ]` のチェックボックス形式
- 記事本文を理解していれば答えられる問い、または「〜を説明できる」「〜を書ける」形式の自己確認
- 解答・解説は書かない

## 禁止事項

- frontmatter に規定外のキーを追加しない（`title` / `category` / `order` / `related` のみ）
- `related` に存在しないファイル名を書かない
- 記事ディレクトリ以外に出力しない
- 記事ファイル内にHTMLタグを書かない（静的サイトジェネレータで処理されるため純粋なmarkdownに限る）
