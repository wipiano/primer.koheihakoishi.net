# C#入門記事ジェネレータ

C#を書き始めたばかりの人が、5分で読んで、翌日から現場で使える記事を生成する。
要点だけを短く、正確に。読み物ではなく、手元に置いて見返すメモに近いものを目指す。

## 対象読者

- C#を触り始めて数週間〜数か月。変数・if・for・メソッド・文字列・`List<T>`の基本操作は書ける
- 業務コードを読むことはあるが、意味が分からないまま真似している箇所が多い
- 専門用語を定義なしに並べられると読むのをやめる。動かないコードを見ると記事への信頼を失う
- 頭は悪くない。知らないだけ。見下さない。「簡単ですよね」「当然ですが」は書かない

## 入力

- `$ARGUMENTS` に記事のテーマ（例: `async/await`, `Nullable参照型`, `Dictionaryの使い方`）と、あれば追加指示（深さ・対象範囲・カテゴリ指定など）が渡される
- テーマが未指定なら、ユーザーに1回だけ確認する。それ以外の判断はすべて自分で行う

## 手順

### 1. 既存記事を調べる

- 出力先ディレクトリ = このskillが置かれた `.claude/` の親ディレクトリ（通常 `pages/csharp/`）。以降「記事ディレクトリ」と呼ぶ
- 記事ディレクトリ直下の `*.md` を Glob で列挙し、各ファイルの frontmatter（`title` / `category` / `order` / `prerequisites` / `next` / `related`）を Grep で読み取る
- 同テーマの記事が既にあれば新規作成せず、その旨を報告して終了（上書き指示があれば上書き）
- 前提記事・次に読む記事の候補と、`order` の分布を把握する

### 2. 前提トピックを洗い出す

「この記事を理解するために読者が知っていなければならないこと」を列挙し、3つに分ける。

- **A. 読者が既に知っている基礎**: 変数・if・for・メソッド・文字列・`List<T>`。記事不要。本文でも説明しない
- **B. 既存記事がある**: frontmatter の `prerequisites` に書く。本文では再説明しない。必要な箇所に限り、記事名を添えて1行で要点を再掲する
- **C. 記事が無い**: **本記事と合わせて生成する**。手順3以降を前提記事から順に実行する

Cのルール:

- 前提記事は本記事より低い `order` にする。前提記事にさらに前提が必要なら、それも生成する（深さは2段階まで）
- 1回の実行で生成する記事は本記事を含めて最大6本。超える分は「未作成の前提記事」として完了報告に書き、その用語は本文中で1文定義して補う
- 同じ実行で生成した記事同士は `prerequisites` と `next` で双方向にリンクしてよい
- 既存記事の frontmatter は変更しない（ユーザーから指示があった場合のみ）

判定基準: その用語を知らないと本文が読めず、かつ1〜2文の定義では足りないなら前提記事。1〜2文で済むなら本文中で定義する。

### 3. メタデータを決める

- **title**: 日本語。「○○の基本」「○○を正しく使う」「○○と○○の違い」のように内容が一目で分かる形。20文字前後
- **category**: 次の7つから1つ
  - `文法` … 言語機能・型システム・構文
  - `設計` … クラス設計、インターフェース、DI、責務分割、命名
  - `パフォーマンス` … メモリ、GC、Span、計測、最適化
  - `非同期` … async/await、Task、並行処理、キャンセル
  - `LINQ` … LINQ全般、IEnumerable、遅延評価
  - `テスト` … 単体テスト、モック、テスト設計
  - `環境・CLI` … dotnet CLI、プロジェクト構成、NuGet、ビルド、デバッグ
- **order**: 難易度を表す1〜100の整数。「その記事を読める人が、既に何ができるか」で決める
  - 1〜20 … 変数・if・forが書ける人向け。型・クラス・メソッド・プロパティ・参照と値・null の基本
  - 21〜40 … クラスを自分で定義できる人向け。コレクション・例外・インターフェース・ジェネリクス・LINQ基礎・null安全・等価性
  - 41〜60 … 業務コードを読める人向け。async/await・DI・record・パターンマッチ・単体テスト・不変設計
  - 61〜80 … 業務コードを書ける人向け。並行処理・Span/Memory・パフォーマンス計測・リフレクション・式木
  - 81〜100 … 設計判断ができる人向け。unsafe・GC内部・ソースジェネレータ・ロックフリー
  - 前提記事は必ず本記事より小さい値にする
- **prerequisites**: 前提記事。各項目は `file`（ファイル名、拡張子付き）と `note`（何が分かっていれば十分かを一言）。0〜3件
- **next**: 次に読む記事。各項目は `file` と `note`（なぜ次に読むとよいかを一言）。0〜3件
- **related**: 前提でも次でもない関連記事のファイル名。0〜3件。無ければ `[]`
- 3つのキーに書けるのは、実在するか同じ実行で生成するファイル名のみ。記事同士のリンクは frontmatter だけに書く。本文中に他記事へのリンクは書かない（ジェネレータは本文中のリンクを解決しない）
- **ファイル名**: ケバブケース英名 + `.md`。2〜5単語。例: `async-await-basics.md`, `nullable-reference-types.md`, `dictionary-usage.md`

### 4. 記事を書く

- 後述「記事の形式」「文体」「コード例」に従う。`template.md`（同じディレクトリ）は形式の見本であり、見出しの文言や数をそのまま使う必要はない
- 記事本文は日本語

### 5. コードを検証する

- すべてのコード例について、後述「コード例」の順序・完結性を目視で確認する
- `dotnet` が使える環境なら、スクラッチディレクトリにコンソールプロジェクトを1つ作り、各コード例を `Program.cs` に貼って `dotnet build` が通ることを確認する。「コンパイルエラーになる」と説明したNG例は、実際にそのエラーが出ることを確認する。通らない例は記事側を直す
- `dotnet` が使えない場合は、その旨を完了報告に書く

### 6. 出力する

- 記事ディレクトリ直下に Write で保存する。前提記事から順に保存する
- 完了報告は次の内容だけを簡潔に伝える
  - 生成した記事ごとに: 出力ファイルパス、title、category、order、prerequisites、next、related
  - 前提記事を合わせて生成した場合はその理由。未作成の前提記事があればそのトピック名と理由
  - コード検証を行ったかどうかと結果

## 記事の形式

見出しの文言・数は固定しない。次の要素を、この順で含める。

1. **定義**: 冒頭で「何であるか」を短い文で述べ、続けて主な性質・目的を箇条書き2〜3個で挙げる。1文にすべてを詰め込まない。見出しやサブタイトルに『record — データを運ぶだけのクラスの省略記法』のような一言のラベルを付けてよい
2. **なぜ必要か**（自明でないときだけ）: 3文以内。これが無いと何が困るかを1つだけ
3. **コード**: 実際に動く最小のコードと、その出力。直後に「何が起きているか」を2〜4文。省略記法（record、プライマリコンストラクタなど）を扱う場合は、省略前の書き方を並べて見せる
4. **最低限の理解**: 覚えておくべきことを箇条書き3〜5個。1項目1〜2文。「これだけ守れば事故らない」運用ルールの形がよい
5. **落とし穴**（必要な場合だけ）: 現場で実際に起きる間違いを1〜2個。NG→OKの順で、NGには出力かエラーを示す。見出しに ⚠️ を付けてよい
6. **課題**: 読者が手を動かす小さな課題を1つ。「自分の担当ドメインで○○を1つ作ってみる」「このコードから1行消したら何が起きるか予想する」のような形。解答は書かない

ルール:

- 本文はコードを除いて800〜1,500文字。読了5分。超えるなら内容を削るか、記事を分ける
- 前提記事で説明した内容は再説明しない。前提記事は frontmatter の `prerequisites` で示されるので、本文で毎回引き直す必要はない。その用語を知らないと直後の文が読めない箇所に限り、記事名を添えて1行で要点を再掲する。「参照型（『参照型と値型の違い』で説明した、変数が実体ではなく場所を指す型）」
- 用語集・理解度チェックリスト・まとめのセクションは作らない。用語は初出時に括弧または1文で定義して終わる
- 「注意点」のためだけのセクションを一般論で埋めない。テーマ固有の注意があるときだけ落とし穴に含める

## 文体

- 常体（「〜だ」「〜する」「〜と覚えればよい」）と体言止め。「〜です」「〜ます」は使わない
- 1文は40文字前後まで。1段落は2〜4文。因果は段落で書き、並列は箇条書きで書く
- **太字**は「これだけ覚えればいい」という1〜2箇所にだけ使う
- たとえ話は書かない。「約束書」「付箋」のような名詞1語のラベルは使ってよいが、直後に本物の用語で言い直す
- 目的を先に、仕組みは後に。仕組みは読者が使うために必要な範囲で止め、IL・JIT・GC内部などテーマの本質でない話には入らない
- 正確さより伝わることを優先する。省いた例外は「厳密には〜だが、まずはこう覚えればよい」と1文で断る
- 中身のない前置きと締めは書かない。「この記事では〜」「いかがでしたか」「ぜひ活用してください」は禁止
- 網羅性より、現場で遭遇する頻度を優先する。マニアックな仕様や歴史的経緯は書かない

## 用語の表記

- 専門用語は初出時に必ず定義する。定義できないなら、その用語を使わずに書く
- 「読者が既に知っている」と見なせる言葉は、変数・if・for・メソッド・引数・戻り値・文字列・配列・`List<T>` だけ
- 一般的な概念を指すときは日本語（カタカナ）で書く。クラス、インターフェース、メソッド、プロパティ、コンストラクタ、インスタンス、オーバーライド
- C#のキーワードや型名そのものを指すときはバッククォートで囲む。`class`、`struct`、`record`、`virtual`、`List<T>`
- `struct` と `record` は、一般的な概念を指すときも英語表記のまま使う（「構造体」「レコード」はタイトルの括弧内のみ）。日本語表記が定着していない用語も同様
- 同じ記事の中で、同じ概念を英語表記と日本語表記で書き分けない

## コード例

- 言語指定付きコードブロック ` ```csharp ` を使う。C# 12 / .NET 8 以降の現行構文（トップレベルステートメント、`var`、Nullable有効前提）
- **そのまま `Program.cs` に貼り付けて `dotnet run` できる状態で書く**
  - トップレベルの文（`var x = ...` や `Console.WriteLine(...)`）は、すべての型定義（`class` / `struct` / `record` / `interface`）より**前**に置く。逆だとコンパイルエラー（CS8803）になる
  - 使うメソッド・変数・型はすべてコード例の中で定義する。`logger` や `_repository` のような「あるものとして」のプレースホルダーは書かない
  - 1ブロックで完結しない場合は、直前に「上の `Point` を使う」のように依存を書く
- `using` は暗黙の `using` で足りないものだけ書く
- 実行結果が出るコードには、直後に出力をコードブロックで示す
- 1つのコード例は20行以内を目安。コメントは日本語で、ポイントの行にだけ
- 変数名・クラス名は `Product`、`Order`、`User`、`Point` のように想像しやすいものにする。`Foo`、`Bar`、`Hoge` は禁止
- 現場で古い言語バージョン（.NET Framework、C# 7系など）に当たる可能性が高い構文（record、`init`、プライマリコンストラクタ、パターンマッチなど）を扱うときは、古い書き方も併記する

## 禁止事項

- frontmatter に規定外のキーを追加しない（`title` / `category` / `order` / `prerequisites` / `next` / `related` のみ）
- `prerequisites` / `next` / `related` に、実在しない・同じ実行で生成しないファイル名を書かない
- 本文中に他記事へのリンクを書かない
- 記事ディレクトリ以外に出力しない（コード検証用の一時プロジェクトはスクラッチディレクトリに作る）
- 記事ファイル内にHTMLタグを書かない（純粋なmarkdownに限る）
- 未定義の専門用語、たとえ話、用語集・理解度チェック・まとめのセクションを書かない
- 貼り付けても動かないコードを載せない
